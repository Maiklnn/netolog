## Задание 1. Резервное копирование

Кейс

Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования.

Необходимо описать, какие варианты резервного копирования подходят в случаях:

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

  
**Ответ**
1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

    Подходящие варианты:
    
    1. Полное резервное копирование (Full Backup) + Дифференциальное (Differential).
    
        - Схема: Полная копия делается, например, в воскресенье. Дифференциальные копии (содержащие все изменения с момента последнего полного бекапа) делаются каждый вечер после завершения рабочего дня.
    
        - Восстановление: Чтобы получить состояние на «вчера», нужно развернуть последнюю полную копию + последнюю дифференциальную копию (за вчерашний вечер). Это быстрее, чем восстанавливать по цепочке журналов транзакций.
    
    2. Ежедневное инкрементное копирование (Incremental) с короткой цепочкой.
    
    - Схема: Полная копия раз в неделю, инкрементные (только изменения) — каждый вечер.
    
    - Нюанс: Для восстановления за вчерашний день придется применить цепочку инкрементов (пн->вт->ср->...->вс), что дольше, чем дифференциальный метод. Поэтому предпочтительнее Full + Differential с ежевечерним запуском.
    
    3. Снапшоты (Snapshot) файловой системы или диска (ZFS, LVM, VMware).
    
        - Ежедневный снапшот на момент 23:59. Восстановление — это откат диска к состоянию предыдущего дня (секунды).

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

    Подходящие варианты:
    
    1. Журналы транзакций (Transaction Log Backup) + Полный бекап.
       
       - Схема: Полная копия делается раз в сутки (ночью). Журналы транзакций (логи изменений) снимаются каждые 15–30 минут (или даже каждые 5 минут при высокой нагрузке).
       
       - Восстановление: Разворачивается последний полный бекап, затем последовательно накатываются все журналы транзакций до временной метки (N-1 час или N-15 минут). Это стандарт для MS SQL, Oracle, PostgreSQL (WAL-архивация).
    
    2. Инкрементное копирование с высокой частотой (Frequent Incrementals).
       
       - Если инкрементные копии делаются каждый час, это тоже подходит. Однако восстановление по инкрементам требует последовательного применения каждого часового файла, что медленнее, чем накат логов.
    
    3. Непрерывная защита данных (CDP — Continuous Data Protection).
       
       - Специализированные софтовые решения (например, для СУБД или виртуальных машин), которые перехватывают каждый блок записи в реальном времени. Позволяют откатиться на любую секунду в прошлом, а не только "за час".


1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных?
    
    Да, это не только возможно, но и является золотым стандартом для финансовых организаций. Это называется Высокая доступность (High Availability, HA) и Аварийное переключение (Failover). Резервное копирование здесь дополняется репликацией.

    1. Синхронная репликация (Synchronous Replication) на уровне СУБД.
    
        - Используется кластер с двумя и более узлами (нодами) (например, PostgreSQL с Patroni, Oracle Data Guard в режиме Maximum Protection, MS SQL Always On).
    
        - Механика: Транзакция считается подтвержденной только тогда, когда она записана одновременно на основном сервере (Primary) и на горячем резерве (Standby). Если Primary падает, кластер автоматически (или по команде администратора) поднимает Standby в качестве мастера.
    
        - Скорость: Переключение занимает секунды (или доли секунды при использовании VIP-адресов и балансировщиков).
    
    2. Репликация на уровне дисков (Storage Replication).
    
        - Используется на СХД (NetApp, Dell EMC). Диски основного сервера синхронно зеркалируются на удаленный СХД. При поломке сервера запускается виртуальная машина на резервном узле, "подхватывая" уже актуальные данные диска.
    
    3. Виртуализация с FT (Fault Tolerance) или Live Migration.
    
        - В средах VMware или Hyper-V работает "теплое" переключение: виртуальная машина с БД работает одновременно на двух хостах (состояние памяти синхронизируется). При падении одного хоста второй продолжает работу без разрыва соединений (для клиента это незаметно).

## Задание 2. PostgreSQL

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?

**Ответ**

2.1. Базовые команды резервирования и восстановления

    Согласно официальной документации PostgreSQL, основная утилита для создания логических резервных копий — pg_dump. Она создает согласованный снимок базы данных, даже во время работы с ней, не блокируя операции чтения и записи для других пользователей.
    
    Команда для резервного копирования (дампа): 
        
        Самый простой способ — создать дамп в виде текстового файла с SQL-командами:
        
        
        pg_dump имя_базы_данных > dump.sql
        Этот файл можно впоследствии передать на вход утилите psql для восстановления.
        
        Однако для производственных сред, особенно в финансах, рекомендуется использовать более гибкие форматы архивов, такие как custom (-Fc). Этот формат сжимает данные по умолчанию и позволяет использовать утилиту pg_restore для выборочного восстановления или параллельной работы.
        
        pg_dump -Fc -h localhost -U postgres имя_базы > backup.dump
        Здесь -h и -U задают хост и пользователя для подключения.
    
    Команда для восстановления (pg_restore):
    
        Для восстановления из архива (формат custom, directory или tar) используется утилита pg_restore.
        
        Чтобы восстановить базу данных в новое состояние, можно использовать ключ -C, который сначала создаст базу данных, а затем восстановит в нее данные:
        
        bash
        pg_restore -C -d postgres backup.dump
        Ключ -d postgres указывает существующую базу данных (например, стандартную postgres), от имени которой будет выполнена команда CREATE DATABASE для восстанавливаемой базы.
        
        Если база данных уже создана, можно восстановить прямо в нее:
        
        bash
        pg_restore -d имя_существующей_базы backup.dump
        В этом случае ключ -C не используется.

2.2. Автоматизация процесса

    Существует несколько подходов к автоматизации, от простых к сложным.
    
    Использование системного планировщика (cron)
        Наиболее распространенный и прямой способ — использование cron для периодического запуска скриптов с командами pg_dump
        0 2 * * * /путь/к/скрипту/backup.sh
        
    Готовые инструменты для продвинутой автоматизации
        - Docker-контейнеры
        - Облачные сервисы
        - Специализированные инструменты для S3

## Задание 3 MySQL

3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.

3.1.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?

**Ответ**

3.1. Пример команды инкрементного резервного копирования MySQL

    Полный бэкап 
        mysqldump --all-databases --single-transaction --master-data=2 > full_backup.sql
    
    Инкрементное копирование 
        изменения, произошедшие после полного бэкапа, хранятся в бинарных логах.
        cp /var/lib/mysql/binlog.000001 /backup/directory/

3.1.* Преимущества использования реплики перед обычным резервным копированием

    Минимальное время восстановления (RTO)
    Нулевая или почти нулевая потеря данных (RPO)
    Разгрузка основного сервер
    Масштабирование для чтения

Однако важно помнить о недостатках: Асинхронная репликация не гарантирует 100% консистентности данных в каждый момент времени (из-за задержек)
