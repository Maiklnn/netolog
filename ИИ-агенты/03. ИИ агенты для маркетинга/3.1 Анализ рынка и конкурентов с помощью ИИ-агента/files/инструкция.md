# Инструкция: развёртывание и запуск агента рыночной аналитики

Документ описывает, как перенести агента на другой сервер n8n, как обновлять его данные
и как запускать прогоны. Проверенная конфигурация, на которой агент собран и работает, —
в конце файла.

---

## 1. Что нужно перед развёртыванием

| Компонент | Требование | Зачем |
|---|---|---|
| n8n | версия 2.8.x (проверено на 2.8.4) | в workflow используются Code-узлы типа `n8n-nodes-base.code` версии 2 и узел агента `@n8n/n8n-nodes-langchain.agent` версии 3.1 |
| Ollama | доступен по HTTP с сервера n8n | модель формирует брифинг |
| Модель | `deepseek-v4.1-flash:cloud` (подойдёт любая instruct-модель, см. п. 6) | генерация текста брифинга |
| Файловая система | каталог, доступный пользователю, под которым работает n8n | в него кладутся исходные данные и пишется готовый брифинг |

Важно: узел «Read/Write Files from Disk» читает файлы **с диска того сервера, где работает
n8n**, а не с машины, из которой вы запускаете браузер.

---

## 2. Установка за пять шагов

### Шаг 1. Скопировать файлы данных на сервер

Каталог данных по умолчанию — `/var/lib/n8n/.n8n-files/market-analyst`. Если он другой,
поменяйте путь в трёх узлах чтения и в узле записи (см. шаг 4).

```bash
ssh -i <ключ> root@<сервер> "mkdir -p /var/lib/n8n/.n8n-files/market-analyst"

scp -i <ключ> data/tariffs.csv      root@<сервер>:/var/lib/n8n/.n8n-files/market-analyst/
scp -i <ключ> data/reviews.csv      root@<сервер>:/var/lib/n8n/.n8n-files/market-analyst/
scp -i <ключ> data/market-review.md root@<сервер>:/var/lib/n8n/.n8n-files/market-analyst/

ssh -i <ключ> root@<сервер> "chown -R n8n:n8n /var/lib/n8n/.n8n-files/market-analyst"
```

`chown` обязателен: файлы, скопированные от `root`, пользователь `n8n` прочитать не сможет,
и узел чтения упадёт с ошибкой доступа.

### Шаг 2. Создать credential для Ollama

В интерфейсе n8n: **Settings → Credentials → Add credential → Ollama**. Укажите базовый URL
(Ollama Base URL). Сохраните и **скопируйте id созданного credential** — он понадобится
на шаге 4.

### Шаг 3. Собрать workflow

```bash
python build-workflow.py
```

Скрипт читает JS-код узлов из `tools/*.js` и системный промпт из `tools/03-system-prompt.md`
и записывает `workflow-market-analyst.json`.

### Шаг 4. Прописать свои значения

В `build-workflow.py` (в начале файла) три константы:

```python
OLLAMA_CRED = {"id": "DEHgfM1I0ZJBmGoo", "name": "Ollama (10.0.2.2:11434)"}  # id из шага 2
MODEL       = "deepseek-v4.1-flash:cloud"                                    # имя модели в Ollama
DATA_DIR    = "/var/lib/n8n/.n8n-files/market-analyst"                       # путь с шага 1
```

После правки — снова `python build-workflow.py`.

### Шаг 5. Импортировать и активировать

```bash
cd tools
python n8n-api.py --import ../workflow-market-analyst.json
python n8n-api.py --list                     # найти id импортированного workflow
python n8n-api.py --activate <workflowId>
```

Активация обязательна: **webhook и расписание работают только у активного workflow.**
Кнопка ручного запуска работает и без неё.

## 3. Запуск

| Способ | Как | Когда нужен |
|---|---|---|
| Расписание | каждый понедельник в 09:00 по времени сервера | регулярный срез к началу недели |
| Кнопка | открыть workflow в интерфейсе → **Execute workflow** | внеплановая проверка, отладка |
| Ссылка (webhook) | `curl http://<сервер>:5678/webhook/market-analyst` | забрать брифинг из внешней системы |

Webhook отвечает JSON-объектом, в котором есть поле `briefing_md` (текст брифинга),
`self_check` (результаты проверок) и `counts` (счётчики прогона).

Прогон занимает **48–80 секунд**; большая часть времени — генерация текста моделью.

### Где искать результат

- **На диске сервера:** `/var/lib/n8n/.n8n-files/market-analyst/briefing-<ГГГГ-ММ-ДД>.md`
  Имя содержит дату прогона, поэтому файл перезаписывается при повторном запуске в тот же
  день. Нужна история — копируйте файл после каждого прогона или меняйте имя в узле
  «Подготовка файла брифинга».
- **В интерфейсе:** узел «Показать брифинг» в последнем выполнении.
- **В списке выполнений:** вкладка **Executions** внутри workflow.

## 4. Обновление данных

Данные обновляются заменой файлов; workflow при этом трогать не нужно.

- **`tariffs.csv`** — прайсы конкурентов. Колонки:
  `school, plan, lessons, lesson_minutes, price_per_lesson, price_from, price_to, format,
  trial_lesson, notes, source_url, checked_date, currency`.
  Колонку `currency` заполнять обязательно (`₽` или `грн`): она протягивается в аналитический
  пакет и защищает модель от сравнения разных валют.
  Если цена неподтверждена, это пишется прямо в `notes` словами «НЕПОДТВЕРЖДЕНО» или
  «актуальность НЕ подтверждена» — агент обязан подавать такие строки с этой пометкой.
- **`reviews.csv`** — отзывы. Колонки:
  `id, school, date, rating, platform, type, category, text, source_url`.
  Поле `date` понимает форматы `2025-03-12`, `12.03.2025`, `12 марта 2025`, `март 2025`
  и просто год. Поле `category` распознаётся по 14 каноническим категориям; если оно пустое,
  категория определится по тексту.
- **`market-review.md`** — дайджест публикаций. Это единственный источник с годовой
  динамикой, поэтому без него в брифинге не будет трендов — только паттерны и гипотезы.

После замены файлов:

```bash
scp -i <ключ> data/tariffs.csv root@<сервер>:/var/lib/n8n/.n8n-files/market-analyst/
ssh -i <ключ> root@<сервер> "chown n8n:n8n /var/lib/n8n/.n8n-files/market-analyst/tariffs.csv"
```

Новые школы достаточно добавить в CSV — справочник названий в узле «Нормализация данных»
ищет совпадение по подстроке, а не по жёсткому списку.

## 5. Проверка после изменений

Локально, без n8n:

```bash
node tools/test-extract.mjs    # регрессионный тест извлечения брифинга из ответа модели
node tools/test-nodes.mjs      # прогон узлов нормализации и фильтрации на реальных данных
```

`test-extract.mjs` стоит запускать после любой правки `tools/04-clean-output.js` — он
воспроизводит реальный сбой, когда модель печатает сначала план с заголовками разделов,
а уже потом сам брифинг.

Оба теста ничего не пишут в `data/`: промежуточные результаты складываются в `tmp/`
(аналитический пакет и нормализованный контекст — их удобно глазами проверить,
если брифинг получился странным).

На сервере — один прогон и проверка результата:

```bash
curl -s http://<сервер>:5678/webhook/market-analyst | head -c 400
```

В ответе должно быть `"self_check_passed": true`. Если `false` — в приложении к брифингу
будет таблица с указанием, какая проверка не прошла.

## 6. Известные особенности и что с ними делать

- **Модель «рассуждающая».** Модели этого класса печатают цепочку размышлений на английском
  (до 19 КБ) и часто повторяют план с теми же заголовками разделов. Узел «Очистка брифинга»
  это учитывает: он ищет по всему тексту полный набор из шести разделов, отбрасывает
  фрагменты с заглушками («...», «3-5 действий.») и берёт самый поздний подходящий. Если
  подходящего фрагмента нет — узел падает с ошибкой, а не отдаёт план вместо брифинга.
  **Замена модели на другую требует проверки этого узла** через `test-extract.mjs`.
- **Валюты.** Если в `tariffs.csv` больше одной валюты, в аналитический пакет автоматически
  добавляется предупреждение, а системный промпт запрещает численно сравнивать разные
  валюты. Это не мелочь: без защиты модель складывает гривны с рублями.
- **Строки «НЕПОДТВЕРЖДЕНО».** Пометка в `notes` работает как ограничение: правило 8
  системного промпта не даёт подать такие данные как факт.
- **Пороги значимости.** `MIN_SIGNAL = 2` и `MIN_INSIGHT = 3` заданы в начале кода узла
  «Фильтрация и группировка». Если данных станет заметно больше, пороги имеет смысл поднять.
- **Ошибка «нет разделов: …».** Означает, что модель не выдала полный брифинг (обычно из-за
  слишком длинного контекста или сбоя модели). Прогон можно просто повторить.

## 8. О зашитом пароле

`tools/n8n-api.py` обращается к REST API n8n и содержит логин и пароль администратора
в открытом виде — так было удобно при сборке на учебном стенде. Перед передачей проекта
куда-либо эти строки нужно заменить чтением из переменных окружения или убрать файл.
