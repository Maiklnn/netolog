# Агент визуальных креативов (n8n)

Практика «Агент визуальных креативов»: агент на n8n, который превращает бриф в
готовые рекламные креативы, сам проверяет их по чек-листу заказчика и складывает
результаты в таблицу и папку на диске.

**Продукт в брифе:** разговорный онлайн-курс английского «Speaking Up» (B1–B2),
бренд **LinguaUp** (вымышленный — реальные логотипы в генеративной графике
воспроизводить нельзя).

---

## Что делает агент

```
Бриф (JSON)  →  LLM-агент-промт-инженер  →  генерация картинок
             →  vision-проверка по чек-листу  →  правка тех, где «нет» > 2
             →  реестр (CSV / Markdown / JSON) + файлы креативов
```

| Шаг | Узел | Что происходит |
|---|---|---|
| 1 | `Входной бриф` | определяет, откуда читать бриф: файл по умолчанию или путь из webhook |
| 2 | `Читать бриф` → `Текст брифа` → `Разобрать бриф` | проверка обязательных разделов брифа и сборка списка вариантов |
| 3 | `Агент: промт-инженер` + `Ollama Chat Model` | LLM превращает бриф в промты: сюжет, свет, композиция, зона под текст |
| 4 | `Собрать промты` | предохранители (битый JSON → запасной промт) и **конструктивная вариативность** |
| 5 | `Генерация FLUX` | публичные генераторы по эшелонам: спейсы HF → Stable Horde → лёгкий размер, если очередь стоит |
| 6 | `Есть ссылка на картинку?` → `Скачать изображение` / `Картинка из base64` | два способа доставки картинки в бинарный вид |
| 7 | `Сохранить изображение` | файл креатива в папку `images` на диске сервера |
| 8 | `Собрать запрос к Vision` → `Vision: проверка` → `Оценка по чек-листу` | ии-арт-директор оценивает креатив по четырём пунктам чек-листа |
| 9 | `Нужна правка?` → `Правка промта` → … | правим **только те** креативы, где ответов «нет» больше двух |
| 10 | `Регистр креативов` → `Сохранить регистр` → `Итог` | сводная таблица, CSV, Markdown и короткая сводка для webhook |

Варианты по брифу:

| Вариант | Площадка | ЦА | Стиль |
|---|---|---|---|
| V1 | Telegram, 1024×1024 | A — «Держусь на работе», 25–35 | минимализм |
| V2 | VK, 1024×1280 | B — «Возвращаюсь к языку», 35–50 | яркий, насыщенный |
| V3 | Яндекс.Директ, 1024×768 | C — «Готовлюсь к переезду», 22–30 | минимализм |
| **V4** | Telegram, 1024×1024 | A — тот же сегмент, что у V1 | **яркий, контрастный** |

V4 — альтернатива V1: **изменён ровно один параметр — стиль** (минимализм → яркий).
Сегмент, площадка, размер, композиция, фокус, акцент, сюжет и сид не меняются.
Это обеспечивается не «обещанием модели», а кодом: узел `Собрать промты` берёт
готовый промт V1 и заменяет в нём один фрагмент, а сид копирует принудительно.

## Как запустить

### Требования

* n8n 2.x (проверено на 2.8.4), сервис запущен;
* Ollama, доступная из n8n по сети (в проекте — `http://10.0.2.2:11434`)
  с моделями `deepseek-v4.1-flash:cloud` (текст и vision);
* **обязательно**: `N8N_RUNNERS_TASK_TIMEOUT=3600` в `/etc/n8n/.env`.
  По умолчанию задача Code-узла обрывается через 5 минут, а запасному
  генератору Stable Horde иногда нужно больше;
* доступ в интернет из контейнера/сервера n8n.

### Установка

```bash
# 1. поднять таймаут Code-узлов и перезапустить n8n
grep -q '^N8N_RUNNERS_TASK_TIMEOUT=' /etc/n8n/.env || \
  echo 'N8N_RUNNERS_TASK_TIMEOUT=3600' >> /etc/n8n/.env
systemctl restart n8n

# 2. положить бриф туда, где его ждёт агент
mkdir -p /var/lib/n8n/.n8n-files/visual-creatives
cp brief.json /var/lib/n8n/.n8n-files/visual-creatives/brief.json

# 3. импортировать workflow
python tools/n8n-api.py --import workflow-visual-creatives.json

# 4. проверить подключение к Ollama (credential «Ollama (10.0.2.2:11434)»)
```

### Запуск

* кнопкой **Execute workflow** в интерфейсе n8n, либо
* по ссылке: `POST http://192.168.56.10:5678/webhook/visual-creatives`
  с телом `{"brief_path": "...", "overrides": {"fix_threshold": 2}}`.
  Параметр `overrides` позволяет поменять настройки, не правя бриф, — например
  снизить порог правки до нуля, чтобы увидеть ветку доработки.

### Где смотреть результат

| Что | Где |
|---|---|
| креативы | `/var/lib/n8n/.n8n-files/visual-creatives/images/` |
| реестр | `/var/lib/n8n/.n8n-files/visual-creatives/registry.{json,csv,md}` |
| краткая сводка | ответ webhook и узел `Итог` в интерфейсе |

## Про генераторы картинок: почему их три эшелона

Изначально в задании был выбран **Pollinations.ai** — он оказался непригоден.
Проверено повторно, уже адресно: эндпоинт отдаёт список моделей `["sana"]`,
а `model=flux` отвечает `200` только на **закешированные** запросы — стоит
поменять сид или промт, и приходит `402 Payment Required` (а `enhance=false`
уходит на модель Sana и падает с `500`). Отдельно проверены варианты с
`safe=true`, `private=true` и другие размеры — результат тот же. Поэтому в агенте
собран трёхэшелонный генератор:

1. **Быстрый эшелон** — публичные спейсы Hugging Face на ZeroGPU
   (`multimodalart/FLUX.1-merged`, `Kwai-Kolors/Kolors`,
   `black-forest-labs/FLUX.1-dev`). Отдают картинку за секунды, но у них квота
   **на IP, а не на запрос**: когда она выбрана, все три спейса за 1–2 секунды
   отвечают `event: error / data: null`, хотя сами остаются в статусе `RUNNING`
   (проверено `tools/generator-probe.py`). Поэтому спейсы проверяются **одним
   пробным запросом** на первом варианте, а не перебором по каждому варианту.
2. **Основной эшелон** — **Stable Horde**, краудсорсинг-сеть воркеров.
   Ключ не нужен (анонимный `0000000000`), квоты нет, отдаёт base64. Но очередь
   анонимного клиента тем длиннее, чем «дороже» задание: у задачи на 512×512 она
   стартует сразу, а у 1024×1024 может стоять 200–400 позиций
   (`tools/horde-size-test.py` меряет это на боевых размерах). Замер 30.09.2026:
   задача 1024×1024 у модели `SDXL 1.0` провисела в очереди 189-й и за 15 минут
   не сдвинулась, а та же сцена 512×512 на модели с родным разрешением 512
   получила `queue_position 0`, 13 свободных воркеров и была готова за 1,9 мин.
   Отсюда и третий эшелон — не «на всякий случай», а рабочий путь.

   **Порог «заслуг».** В часы нагрузки сервис вообще закрывает крупные запросы:
   `403 KudosUpfront` — «Due to heavy demand, for requests over 1024×1024 or over
   the applicable first-order-equivalent sampler work budget the client needs to
   already have the required kudos». Замер `tools/horde-queue-probe.py`
   (30.09.2026, вечер): задача 1024×1024 у `SDXL 1.0` стояла **295-й** и не
   начиналась, а та же сцена 512×512 — нулевой. Порог считается по площади и
   числу шагов, поэтому список из нескольких SDXL-моделей его тоже перешагивает:
   он оценивается дороже одной модели (20.03 против 18.0) и был отклонён.
   Отсюда правило — у основного эшелона ровно одна модель, а лёгкий запас в такие
   часы становится основным путём. Имена моделей проверены тем же замером:
   несуществующее имя Stable Horde отбивает как `faulted`.
3. **Лёгкий запас** — если за 3 минуты ни одна задача основного эшелона не
   сдвинулась с места, недостающие варианты досылаются в уменьшенном размере
   (те же пропорции, площадь вчетверо меньше) **на другой модели** — с родным
   разрешением 512 (`AbsoluteReality`, `Realistic Vision`, `Deliberate`).
   Это не мелочь: SDXL 1.0 рассчитан на 1024 и на 512 уходит в плоскую
   стилизацию, из-за чего «запасные» картинки выходили абстрактными.
   Фактический размер пишется в поле `size_actual`, модель — в `generator`,
   признак понижения — в `size_downgraded`.

   **Подбор моделей лёгкого эшелона.** В прогоне 86 тяжёлый размер не пришёл
   вовсе, и все четыре креатива вышли лёгким запасом — то есть этот эшелон стал
   основным путём. Тогда и выяснилось, что в списке стояла base-модель
   `stable_diffusion`: она нарисовала «руки над блокнотом» вместо героини у
   стола, и чек-лист справедливо поставил варианту «нет» за соответствие брифу.
   Сравнение на одном промте (`tools/horde-model-pick.py`, 512×512, 30 шагов)
   показало разницу прямо: финетюны держат сцену и брендовую палитру, base-модель
   её теряет, а SDXL 1.0 на 512 уходит в плоскую стилизацию (женщина «в рамке на
   стене»). Поэтому base-модель из списка убрана, `AbsoluteReality` поставлен
   первым, а число шагов лёгкого запаса поднято с 20 до 30.

   Тяжёлые задачи при этом не бросаются: когда все варианты уже закрыты, узел
   даёт живым тяжёлым задачам ещё `HORDE_UPGRADE_GRACE_MS` (8 минут), и если
   тяжёлая картинка успевает — она **заменяет** лёгкую. Раньше цикл выходил
   ровно в тот момент, когда закрывалась последняя «дырка», и лёгкий размер
   оставался в результате навсегда, хотя тяжёлая задача ещё стояла в очереди
   и её никто не ждал. Что именно произошло, видно в реестре: поле
   `generator_note` перечисляет ход ожидания, а `size_downgraded: true`
   означает, что тяжёлый размер так и не догнал.

**Лимит запросов.** Анонимному клиенту Stable Horde разрешает около одного
запроса в секунду и отвечает `429`, если частить. Первая версия узла опрашивала
очередь пачкой запросов подряд — пачка выбирала лимит, отправка лёгкого размера
падала с ошибкой, и узел честно ждал тяжёлую очередь до самого потолка в 35
минут. Теперь между отправками пауза 1,5 с, между опросами — 0,4 с, а неудачная
отправка лёгкого размера повторяется в следующем круге (до пяти попыток на
вариант, чтобы не долбить сервис до потолка).

**Наблюдаемость.** У workflow включён `saveExecutionProgress`. Без него n8n не
пишет состояние узлов до конца выполнения, и по API у долгого прогона виден
пустой `runData`: непонятно, стоит он на очереди чужого сервиса или завис.
С включённым флагом прогресс читает `tools/watch-exec.py <id>`, а в интерфейсе
n8n узлы подсвечиваются по мере прохождения.

**Про время.** Приоритет анонимного клиента в Stable Horde сильно плавает: замеры
в один и тот же час дали и `queue_position 0` для 512×512, и `204` для 512×640
(скорость разбора очереди — около 0,2 позиции в секунду, то есть 200 позиций это
примерно 16 минут). Поэтому пакет из четырёх креативов может идти и минуту, и
двадцать. Лёгкий размер здесь не панацея: он помогает, только когда очередь
короткая, а при заторе встаёт в неё вместе с тяжёлым. Если нужен предсказуемый
результат — запускать в спокойные часы.

Общий потолок ожидания — 35 минут на пакет. Что не подошло совсем: локальная
генерация на сервере (нет GPU, нет ComfyUI/A1111 — проверены порты 7860, 7861,
8188, 11434) и Stable Diffusion на CPU-спейсах.

## Правка: почему она не трогает сид

По условию задания на правку уходят **только** креативы с более чем двумя «нет».
Правка дописывает в промт уточнения по проваленным пунктам чек-листа (по одному
блоку на пункт) и больше ничего не делает — **сид остаётся тем же**.

Так было не всегда. Сначала узел `Правка промта` брал новый сид
(`seed + 1000 × попытка`) — казалось логичным: с тем же сидом и почти тем же
промтом выйдет почти та же картинка, и ошибка не исправится. Но у этого решения
оказалась цена поважнее: альтернатива **V4** — это V1 с изменённым ровно одним
параметром, и сид для неё копируется от V1 принудительно. Как только правка
уводила сид, пара V1/V4 расходилась по кадру, и поле «чем отличается результат»
описывало уже две разные сцены вместо разницы стилей. В прогоне 87 в правку
попал V1, а V4 — нет, и сравнивать их стало нечем.

Ещё одно следствие того же прогона: реестр оставлял **более позднюю** попытку
безусловно, и у V1 в таблицу попадал вариант с 4 «нет», тогда как первая попытка
давала 3. Теперь побеждает попытка с меньшим числом «нет», а при равенстве —
первая (она сохраняет исходный кадр). Попытка без оценки не участвует в сравнении:
у неё в чек-листе стоят «н/д», и по числу «нет» она выглядела бы лучше всех.
Если правка отработала и проиграла, это сказано прямо — в комментарии, и в
столбцах «Попыток» / «Правка выполнена» таблицы.

## Технические находки этого n8n

Две особенности, из-за которых пришлось переделать схему (обе проверены
диагностикой `tools/probe-binary-roundtrip.py` и `tools/probe-binary.py`):

1. **Бинарники хранятся в файловом режиме.** В `binary.data.data` лежит не
   base64, а ссылка `filesystem-v2`. Настоящие байты внутри Code-узла даёт
   только `await this.helpers.getBinaryDataBuffer(index, 'data')`.
2. **Code-узел не умеет скачивать картинку по сети.** `helpers.httpRequest`
   возвращает побитую строку: тестовый webp приходит как 28 710 «байт» вместо
   30 320. Зато base64, полученный обычным JSON, Code-узел превращает в файл
   без потерь — md5 записанного файла совпадает с исходным. Отсюда и две ветки
   после генератора: ссылку скачивает узел HTTP Request, base64 собирает
   Code-узел.

Дополнительно: узел HTTP Request в режиме «файл» (`responseFormat: file`)
сохраняет поля JSON, а в режимах `json`/`text` — заменяет их целиком.

Ещё две находки, обе всплыли, когда заработал запасной генератор (до этого
ветка base64 ни разу не доходила до сохранения файла):

3. **Ответ агента приходил с испорченным началом JSON.** У модели-рассуждалки
   `deepseek-v4.1-flash:cloud` в узле `Ollama Chat Model` не был включён
   встроенный `Output Format` — без него модель писала прозу и до JSON не
   доходила. Включение `Output Format = JSON` проблему закрыло не полностью:
   модель сначала печатает длинное размышление, потом JSON, и узел отдаёт
   это одной строкой. На склейке теряются первые символы объекта — в прогоне
   83 пришло `…Let me finalize.variants":[…]}»` вместо
   `…Let me finalize.{"variants":[…]}`, а в прогоне 84 — `…Output JSON only.ants":[…]}»,
   то есть уже вместе с именем ключа. Прямой разбор `JSON.parse` от первой `{`
   до последней `}` на таком тексте падает, узел молча уходит на запасные
   промты из брифа, и работа LLM-агента пропадает целиком (в реестре это
   выглядит как `prompt_source: fallback`).
   Теперь `extractJson` в `03-build-prompts.js` трёхступенчатый: прямой разбор
   → поиск сбалансированного массива, элементы которого похожи на варианты
   (объекты с полем `id`), с восстановлением имени ключа → поиск любого
   сбалансированного объекта с массивом `variants`. Скобки внутри строк при
   этом не считаются, а корректный, но посторонний объект из прозы ответ не
   подменяет. Разбор проверяется на обоих боевых ответах:
   `node tools/test-extract-json.js`.
4. **Имя файла никто не задавал.** Узел `Сохранить изображение` берёт путь
   выражением `{{ $json.file_name }}`, а на основном пути это поле не
   заполнялось: в ветке правки его ставит `07-fix-prompt.js`, в ветке base64 —
   `04b-image-from-b64.js`, а до них — никто. В итоге все четыре варианта
   писались в один и тот же `undefined.webp`, затирая друг друга. Теперь имя
   задаётся сразу в `03-build-prompts.js`, а расширение оба генератора
   переписывают по фактическому формату картинки.
5. **Запреты уходили в генератор по-русски.** Агент писал поле `negative` так
   же, как сформулированы запреты в брифе, — по-русски. Диффузионная модель
   читает промт английским CLIP: для неё русские слова не текст, а случайный
   набор токенов, то есть запретов не было вообще. Теперь системный промт
   требует `negative` только на английском, а в `04-generate.js` стоит проверка
   языка: если в строке есть кириллица, вместо неё подставляется английский
   список запретов, собранный из `restrictions.forbidden_elements` брифа.
   В реестре видно и то, что ушло в генератор (`запреты`), и откуда оно взялось.
6. **Правка промта дописывала в кадр русский текст.** Узел `Правка промта`
   собирал уточнения из русских полей брифа — стиля, зоны под текст, портрета
   ЦА — и приклеивал их к англоязычному промту. По той же причине, что и в
   пункте 5, генератор получал не уточнение, а шум: в прогоне 82 после правки
   у V4 стало 4 ответа «нет» вместо 3, то есть стало хуже. Для полей, которые
   идут в промт, в брифе добавлены английские двойники (`style_en`, `focus_en`,
   `segments[].who_en`, `placements[].text_zone_en`), а из промта на выходе
   кириллица вырезается — с пометкой в реестре, если это пришлось сделать.
