# Инструкция: развёртывание и запуск агента контент-плана

Документ описывает, как перенести агента на другой сервер n8n, как обновлять его данные
и как запускать прогоны. Проверенная конфигурация, на которой агент собран и работает, —
в конце файла.

---

## 1. Что нужно перед развёртыванием

| Компонент | Требование | Зачем |
|---|---|---|
| n8n | версия 2.8.x (проверено на 2.8.4) | в workflow используются Code-узлы версии 2, узлы `n8n-nodes-base.if` версии 2.2 и узел агента `@n8n/n8n-nodes-langchain.agent` версии 3.1 |
| Ollama | доступен по HTTP с сервера n8n | модель строит план и пишет материалы |
| Модель | `deepseek-v4.1-flash:cloud` (подойдёт любая instruct-модель, см. п. 6) | генерация плана и текстов |
| Файловая система | каталог, доступный пользователю, под которым работает n8n | в него кладутся исходные данные, в него же агент пишет готовые файлы |

Важно: узлы «Read/Write Files from Disk» читают и пишут файлы **на диске того сервера,
где работает n8n**, а не на машине, где открыт браузер.

Отдельно нужны **две** модели или один и тот же credential дважды — в workflow два узла
`Ollama Chat Model` с разными настройками (стратег и копирайтер).

## 2. Установка за пять шагов

### Шаг 1. Скопировать файлы данных на сервер

Каталог данных по умолчанию — `/var/lib/n8n/.n8n-files/content-agent`. Если он другой,
поменяйте путь в трёх узлах чтения и в двух узлах записи (см. шаг 4).

```bash
ssh -i <ключ> root@<сервер> "mkdir -p /var/lib/n8n/.n8n-files/content-agent"

scp -i <ключ> data/brand-brief.md   root@<сервер>:/var/lib/n8n/.n8n-files/content-agent/
scp -i <ключ> data/content-rules.md root@<сервер>:/var/lib/n8n/.n8n-files/content-agent/
scp -i <ключ> data/content-log.csv  root@<сервер>:/var/lib/n8n/.n8n-files/content-agent/

ssh -i <ключ> root@<сервер> "chown -R n8n:n8n /var/lib/n8n/.n8n-files/content-agent"
```

`chown` обязателен: файлы, скопированные от `root`, пользователь `n8n` прочитать не сможет,
и узел чтения упадёт с ошибкой доступа.

### Шаг 2. Создать credential для Ollama

В интерфейсе n8n: **Settings → Credentials → Add credential → Ollama**. Укажите базовый URL
(Ollama Base URL). Сохраните и **скопируйте id созданного credential** — он понадобится
на шаге 4.

### Шаг 3. Собрать workflow

```bash
python build-workflow.py
```

Скрипт читает JS-код узлов из `tools/*.js`, системные промпты из
`tools/02-strategist-prompt.md` и `tools/04-copywriter-prompt.md` и записывает
`workflow-content-agent.json` (26 узлов).

### Шаг 4. Прописать свои значения

В `build-workflow.py` (в начале файла) три константы:

```python
OLLAMA_CRED = {"id": "DEHgfM1I0ZJBmGoo", "name": "Ollama (10.0.2.2:11434)"}  # id из шага 2
MODEL       = "deepseek-v4.1-flash:cloud"                                    # имя модели в Ollama
DATA_DIR    = "/var/lib/n8n/.n8n-files/content-agent"                        # путь с шага 1
```

Расписание задано там же, в узле «Расписание (еженедельно, Чт 10:00)»: раз в неделю, четверг, 10:00
(`field: weeks`, `weeksInterval: 1`, `triggerAtDay: [4]`, `triggerAtHour: 10`).
После правки — снова `python build-workflow.py`.

### Шаг 5. Импортировать и активировать

```bash
cd tools
python n8n-api.py --import ../workflow-content-agent.json
python n8n-api.py --list                     # найти id импортированного workflow
python n8n-api.py --activate <workflowId>
```

Активация обязательна: **webhook и расписание работают только у активного workflow.**
Кнопка ручного запуска работает и без неё.

## 3. Запуск

| Способ | Как | Когда нужен |
|---|---|---|
| Расписание | каждый четверг в 10:00 по времени сервера | регулярный план на следующую неделю |
| Кнопка | открыть workflow в интерфейсе → **Execute workflow** | внеплановая проверка, отладка |
| Ссылка (webhook) | `curl http://<сервер>:5678/webhook/content-plan` | забрать план из внешней системы |

Webhook отвечает JSON-объектом: `plan_period` (период плана), `plan` (7 публикаций),
`document_md` (готовый документ по структуре шаблона ДЗ), `demo_rows` (расписание
для демо-среды), `checklist` (шесть ответов самооценки), `verdict`, `checks_passed`,
`checks_total`, `attempts`.

Прогон занимает **33–40 секунд**; большая часть времени — два обращения к модели.

### Где искать результат

- **На диске сервера:**
  - `/var/lib/n8n/.n8n-files/content-agent/content-plan-<ГГГГ-ММ-ДД>.md` — документ целиком;
  - `/var/lib/n8n/.n8n-files/content-agent/demo-schedule-<ГГГГ-ММ-ДД>.csv` — расписание
    для демо-среды (14 строк, разделитель `;`, UTF-8 с BOM).

  Имя содержит дату начала плана, поэтому повторный запуск в тот же день перезапишет файл.
  Нужна история — копируйте файлы после каждого прогона или меняйте имя в узлах
  «Подготовка файла (Markdown)» и «Подготовка файла (CSV)».
- **В интерфейсе:** узел «Показать результат» в последнем выполнении.
- **В списке выполнений:** вкладка **Executions** внутри workflow.

## 4. Обновление данных

Данные обновляются заменой файлов; workflow при этом трогать не нужно.

- **`content-log.csv`** — журнал публикаций. Колонки:
  `id;date;platform;rubric;task;topic;format;status;views;reactions;comments;saves;er_percent`
  (разделитель — точка с запятой). Агент считает по журналу ER отдельно по рубрикам,
  задачам и форматам и передаёт выводы стратегу, поэтому старые записи удалять не нужно:
  чем длиннее журнал, тем устойчивее статистика.
  Поле `topic` участвует в проверке «темы не повторяют публикации последних двух недель» —
  именно по нему агент отсекает повторы, так что темы нужно писать так же, как в плане.
- **`content-rules.md`** — правила контента: периодичность, баланс задач, рубрики, форматы,
  требования площадок, запрещённые формулировки, лестница статусов. Это второй источник
  ограничений после кода проверок: если менять требования, то и здесь, и в промптах.
- **`brand-brief.md`** — бриф бренда: продукт, цель, ЦА, боли, потребности,
  позиционирование, тон.

После замены файлов:

```bash
scp -i <ключ> data/content-log.csv root@<сервер>:/var/lib/n8n/.n8n-files/content-agent/
ssh -i <ключ> root@<сервер> "chown n8n:n8n /var/lib/n8n/.n8n-files/content-agent/content-log.csv"
```

Список рубрик, форматов и задач зашит в узлы проверок (`tools/03-parse-plan.js`) —
новую рубрику недостаточно дописать в правила: её нужно добавить в константы `RUBRICS`,
`FORMATS` или `TASKS`, иначе проверка «нет посторонних рубрик и задач» забракует план.

## 5. Проверка после изменений

Синтаксис узлов — до отправки в n8n:

```bash
node --check tools/01-prepare-input.js
node --check tools/03-parse-plan.js
node --check tools/05-parse-content.js
```

`node --check` только разбирает файл и ничего не выполняет: узловые переменные
(`$json`, `$runIndex`, `helpers`) в обычном node не существуют, но ошибку в скобках
это поймает.

На сервере — один прогон и проверка ответа:

```bash
curl -s http://<сервер>:5678/webhook/content-plan | head -c 600
```

В ответе должно быть `"verdict": "Все проверки пройдены"` и
`"checks_passed": 22` при `"checks_total": 22`. Если проверки не прошли — в поле
`failed_checks` будет список с деталями, а в `attempts` видно, сколько раз агент
перегенерировал план и материалы.

**После правки кода узла одной только заливки мало.** `python n8n-api.py --update
<workflowId> <файл>` обновляет workflow, но n8n не подхватывает изменённый код узлов,
пока workflow не переактивирован:

```bash
cd tools
python n8n-api.py --update <workflowId> ../workflow-content-agent.json
python n8n-api.py --activate <workflowId>
```

## 6. Известные особенности и что с ними делать

- **Модель «рассуждающая».** Модели этого класса проговаривают ход мысли и набрасывают
  черновики прямо в ответе. Поэтому оба промпта требуют маркеры структуры, а разбор
  (`tools/05-parse-content.js`) ищет **последнее** вхождение закрывающего маркера: черновик
  остаётся левее и в материал не попадает. **Замена модели на другую требует проверки
  этих узлов** — прогоном по ссылке и просмотром ответа.
- **Проверки не роняют прогон.** Брак не выбрасывает исключение, а возвращает работу
  на пересборку: не больше двух попыток, после чего агент идёт дальше и честно пишет
  об этом в отчёте. Счётчик попыток — системная переменная `$runIndex`.
  Считать попытки через `$('Узел').all().length` нельзя: в цикле узел отдаёт данные
  с накоплением, и лимит не срабатывает — цикл не сходится.
- **Неразобранный ответ — не ошибка, а повтор.** Если модель ответила текстом вместо JSON,
  узел «Разбор контент-плана» на первой попытке отправляет стратегу задание заново вместе
  с началом неудачного ответа. Исключение бросается только на второй попытке: дальше идти
  не с чем, и это честная ошибка.
- **Лимиты площадок продублированы в конце задания.** Telegram — до 900 символов без
  хэштегов, ВКонтакте — до 1400 символов и не больше 3 хэштегов с вопросом к читателю.
  Короткое напоминание в последнем сообщении работает надёжнее абзаца в системном промпте;
  если менять лимиты — правьте и промпт, и константы `telegram_limit`/`vk_limit`
  в `tools/05-parse-content.js`.
- **Запрещённые формулировки.** Проверка ищет корни слов подстрокой («гарантир»,
  «уникальн») и отдельные слова по границам («срочно», «лечит») — иначе «срочность» ловится
  как «срочно». Список — в `BANNED_STEMS` и `BANNED_WORDS` того же узла; тот же список
  перечислен в промпте копирайтера, чтобы модель не доводила дело до переписывания.
- **Даты плана.** «Подготовка входных данных» считает календарь от ближайшего понедельника
  по времени сервера. Если сервер живёт в UTC, а заказчик — в другом поясе, план будет
  сдвинут на день: проверьте `TZ` у сервиса `n8n`.
- **Статус публикаций.** Агент ставит в расписание статус **«на проверке»** и никогда
  не поднимает его выше сам. Это осознанное ограничение: ни одна публикация не уходит
  на площадку без человека.

## 8. О зашитом пароле

`tools/n8n-api.py` обращается к REST API n8n и содержит логин и пароль администратора
в открытом виде — так было удобно при сборке на учебном стенде. Перед передачей проекта
куда-либо эти строки нужно заменить чтением из переменных окружения или убрать файл.
